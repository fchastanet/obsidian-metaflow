# AI Prompts

## Task: Refactor File Event Processing Algorithm for FileClassStateManager

**Objective:** Refactor the file event processing system to use a simpler, robust, and maintainable algorithm that:

- Registers all file events in a queue or map structure.
- Uses a deterministic checksum approach to ignore plugin-generated events.
- Debounces events, keeping a full, ordered history of event types per file until processed.
- Processes events in batches at regular intervals (via cron or timer).
- Integrates with Obsidian’s file system events and plugin lifecycle.
- do not remove any existing class, create new classes in a new folder.

## Requirements

### 1. Event Registration & Debouncing

- All file events (create, change, rename, delete) are registered in a per-file event history structure.
- The event history is ordered and accumulates until processed by the cron.
- The cron runs at a regular interval, so the event history is naturally limited in size.
- Event queue must support burst handling and conflict resolution.

### 2. Processing Rules

- If a file is deleted in the batch, skip all processing for that file.
- If a file is both changed and renamed, process only the rename.
- If a file is changed and then moved by the plugin (causing a second batch of change+rename), ignore the entire batch.
- Identify and handle other similar cases where events should be ignored or collapsed.
- When process is executed, events that happened during the processing should be ignored (update fileStateCache checksum
  before saving the file).

### 3. Deterministic Filtering

- When the plugin processes a file, it updates the file’s checksum in a cache.
- If, during processing, the current checksum matches the cached one, the event is ignored (as it was generated by the
  plugin).

### 4. State and Cache Management

- Use LRU eviction for the file state cache, with configurable size.
- Include a dirty flag and versioning in the cache for conflict detection and pending writes.
- Implement periodic cleanup of deleted files and stale cache entries.
- Track renaming, deleted, and processing files with appropriate structures and TTLs.

### 5. Processing Locks and Concurrency

- Use processing locks to prevent simultaneous processing of the same file.
- Track operation type and start time for timeout detection and recovery.

### 6. Error Handling and Recovery

- Categorize errors (file system, processing, concurrency, plugin integration).
- Provide user notifications for errors via LogNoticeManager.
- No need for automatic retry with exponential backoff or rollback support.

### 7. Performance and Monitoring

- Collect metrics on processing times, cache hit rates, event frequencies, and error rates.
- Implement adaptive debouncing and burst detection for event queue management.
- Support batch processing and event coalescing for efficiency.

### 8. Testing and Validation

- Comprehensive unit and integration tests, including edge cases and bulk operations.
- Mock Obsidian’s file system and plugin interactions for testing.
- Validate performance, reliability, and user experience metrics.

### 9. Extensibility and Configuration

- Allow user-configurable rules for event filtering, processing, debounce timings, and cache sizes.
- Provide a clear API for integration with other plugins and external tools.

### 10. Edge Case Handling

- Handle simultaneous and overlapping events, vault-wide operations, and external file system changes.
- Support for fileClass definition changes and vault renames/moves.

### 11. User Experience

- Provide progress indicators, conflict resolution UI, and clear error messages.
- Ensure accessibility and theme integration.

Deliverables:

- Propose at least two alternative algorithms or data structures that meet these requirements.
- For each, describe the event queue structure, debouncing logic, and event collapsing/filtering rules.
- Provide pseudocode or TypeScript code snippets for the core logic.
- Identify any additional edge cases and how they are handled.
- Ensure the new algorithm is easy to maintain and extend for future event types or rules.

Success Criteria:

- The new algorithm must avoid infinite loops from plugin-generated events.
- It must efficiently process only necessary events, skipping redundant or obsolete ones.
- It must be robust, maintainable, and extensible.
- It must integrate seamlessly with Obsidian and other plugins.
- It must provide clear feedback and error reporting to users.
